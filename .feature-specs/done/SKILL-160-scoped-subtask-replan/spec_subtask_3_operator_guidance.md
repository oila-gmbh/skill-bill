# SKILL-160 · Subtask 3 — Operator guidance in the governed skills

Parent spec: `.feature-specs/SKILL-160-scoped-subtask-replan/spec.md`

## QA Statement

An agent that amends a subtask spec partway through a prepared goal reads the governed skill
content, reaches for `skill-bill goal replan <key> --subtask <id>`, and continues — instead of
running a goal-wide hard reset and then rebuilding the state that reset destroyed with
compensating `accept --restore-after-hard-reset` calls.

## Why this is its own subtask

For skill-bill the governed skill content is a shipped product surface, not documentation about the
product. An agent's behaviour is determined by what the skill text tells it to do, so a runtime
capability no skill mentions is unreachable in practice — the hard-reset workaround will keep being
chosen because that is what the text currently sanctions.

`bill-feature/SKILL.md` today says, of a subtask whose work landed outside the runtime: *"Do not
edit `decomposition-manifest.yaml` to force progress"* and points at `goal accept`.
`bill-feature-goal.md` says: *"Hard reset atomically invalidates parent planning and child
continuation state; soft reset preserves compatible immutable planning."* Between them there is no
scoped-replan option, which is why the observed workaround was the only reading available.

## Scope

Update the governed skill content so scoped replan is the sanctioned response to a mid-goal spec
amendment. Write the flags exactly as subtasks 1 and 2 shipped them — read the implementation, do
not restate this spec's proposed spelling if it drifted.

### 1. `bill-feature-goal.md`

The planning paragraph currently presents hard reset and soft reset as the only two planning
outcomes. Add scoped replan as the first-choice tool for the amended-spec case, covering:

- when to reach for it — a subtask spec changed after that subtask's plan was already checkpointed,
  which resume would otherwise ignore because settled planning is not regenerated by branch changes;
- what it preserves — sibling plans, the shared preplan by default, and every subtask's terminal
  state, `commit_sha`, `workflow_id` and out-of-band acceptance;
- when `--include-shared-preplan` is warranted, and the provenance consequence subtask 2 settled;
- that it requires an idle goal, and what the live-goal refusal means;
- that a terminal subtask is refused, with `reset` named as the operation for that case.

Keep the existing hard/soft reset text accurate rather than deleting it. Hard reset remains correct
for goal-wide invalidation; the change is that it stops being the *only* documented path to a
replan.

### 2. `bill-feature/SKILL.md`

Its continuation-handling rules are where an agent decides what to do with an existing prepared
goal. Add the amended-spec case alongside the existing `goal accept` guidance, in the same voice:
an amended subtask spec is a replan, not an acceptance and not a manifest edit. Reinforce the
existing prohibition — hand-editing `decomposition-manifest.yaml` is still never the answer — and
name replan as the supported alternative.

### 3. Guard against the workaround

Both files should make it explicit that hard reset followed by compensating
`accept --restore-after-hard-reset` calls is not the way to replan a single subtask, and say why:
it discards every completed subtask's `commit_sha` and `workflow_id` and forces the operator to
reconstruct the commit-to-subtask mapping by hand. An agent that has only seen the old text will
otherwise keep reproducing it.

### 4. Keep the surfaces consistent

- If `skill-bill goal --help`'s command list or any other operator-facing help text enumerates the
  goal subcommands, `replan` belongs there too.
- Check whether any other governed skill or sidecar describes planning invalidation or goal reset,
  and update it in the same pass. A single stale copy is enough to send an agent back to hard reset.

## Acceptance Criteria

1. `bill-feature-goal.md` documents scoped replan as the first-choice response to a mid-goal spec
   amendment, covering when to use it, what it preserves, the `--include-shared-preplan` case, the
   idle-goal requirement, and the terminal-subtask refusal naming `reset`.
2. `bill-feature/SKILL.md`'s continuation rules name replan as the supported handling for an amended
   subtask spec, alongside the existing `goal accept` guidance, and keep the prohibition on
   hand-editing `decomposition-manifest.yaml`.
3. Both files state explicitly that hard reset plus compensating
   `accept --restore-after-hard-reset` is not how to replan one subtask, and give the reason.
4. The existing hard-reset and soft-reset guidance remains present and accurate; nothing about
   `reset`'s documented behaviour is misstated.
5. Every flag, subcommand and refusal message quoted in the skill content matches what subtasks 1
   and 2 actually shipped, verified against the implementation rather than against this spec.
6. `replan` appears in the goal subcommand list in operator-facing help output, and no other
   governed skill or sidecar still presents hard reset as the only way to invalidate planning.
7. The repository's check gate passes, including whatever content-hash or governed-skill validation
   the repo applies to skill files.

## Non-Goals

- Any runtime, CLI or persistence change. This subtask is content only; if it uncovers a behavioural
  gap, that is a finding to raise, not to fix here.
- Rewriting the reset documentation beyond what is needed to keep it accurate next to replan.
- Changing `accept --restore-after-hard-reset` or its guidance for the cases hard reset is still
  right for.

## Dependency Notes

Depends on subtasks 1 and 2. The guidance must describe the command and flags as shipped, including
the exact refusal messages and the provenance resolution subtask 2 chose — none of which is
knowable until both have landed. Writing this first would guarantee documentation that drifts from
the implementation in its first commit.

## Validation Strategy

- Cross-read every quoted flag, subcommand and message against the implementation from subtasks 1
  and 2; a mismatch is a defect in this subtask.
- Confirm `skill-bill goal --help` lists `replan`.
- Grep the governed skill and sidecar content for remaining descriptions of planning invalidation
  and reset, and confirm none still implies hard reset is the only path.
- The repository's check gate, including governed-skill content validation.
